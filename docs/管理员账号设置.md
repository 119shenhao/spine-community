# Spine Community 管理员账号设置（两种方式）

> 更新日期：2026-11-10。适用于当前 `main` 生产代码与 `feature/v1-community-build-20261106` 开发预览代码。
>
> **两种方式均已由源码确认可用。** 方式一适合手动授予现有账号管理员权限；方式二适合通过 Cloudflare 环境变量，在 Google 登录时自动初始化管理员。设置方法本身不会创建 Google 账号，用户必须通过本站 Google 登录完成注册。
>
> 本文是**操作手册**，记录配置与 SQL；仅编写本文不代表已经操作 Cloudflare、修改 D1、变更权限或部署网站。

## 环境区分

| 环境 | 网站及身份接口 | 授权位置 |
| --- | --- | --- |
| 开发预览（Preview） | [开发站](https://feature-v1-community-build-20261106-spine-community.119shenhao.workers.dev/) / [`/api/me`](https://feature-v1-community-build-20261106-spine-community.119shenhao.workers.dev/api/me) | 预览所绑定的开发 D1；Cloudflare Preview 的变量与机密 |
| 生产（Production） | [正式站](https://spine.nbn369.com/) / [`/api/me`](https://spine.nbn369.com/api/me) | 生产所绑定的 D1；Cloudflare Production 的变量与机密 |

开发与生产的 **D1 数据库互相独立**，即使是同一个 Google 账号也可能有不同的本站 `users.id`。两边如需管理员权限，必须分别授权；**不要将开发用户 ID 原样用于生产 SQL**。先核对当前要操作的是哪个数据库及绑定，尤其在生产环境。

论坛当前有两种角色：`admin`（站长管理员）和 `moderator`（版主）。下述 SQL 的 `admin` 表示最高业务管理角色。后台页面入口为 `/#/admin`。

## 方式一：通过网页查本站用户 ID，再执行 D1 SQL（手动授权，推荐）

**无需设置 `ADMIN_GOOGLE_SUB`，也无需修改代码或重新部署。**

1. 使用希望成为管理员的 Google 账号登录**目标环境**的论坛。
2. 在同一个浏览器登录会话中打开目标站点的 `/api/me`（上方表格有直达链接），查看 `user.id`。正常返回类似：

   ```json
   {
     "user": {
       "id": "example-user-id",
       "nickname": "Member",
       "role": "member"
     },
     "googleConfigured": true
   }
   ```

   只复制 `user.id`（本站内部 ID）；`role` 目前是 `member` 很正常。如果返回 `user: null`，先回论坛登录并确认浏览器会话没有切换。**不要把这里的用户 ID 误当成 Google Subject ID。**

3. 进入 [Cloudflare Dashboard](https://dash.cloudflare.com/) → **Storage & databases / 存储和数据库 → D1 → 目标环境的 D1 → Console**。再次核对开发 / 生产及数据库绑定。
4. 在该 D1 中执行（用真实 `user.id` 替换占位符；保留单引号）：

   ```sql
   INSERT OR IGNORE INTO user_roles (user_id, role)
   VALUES ('替换成当前环境的user.id', 'admin');
   ```

   `INSERT OR IGNORE` 可避免重复添加相同角色；数据库 `user_roles` 的键为 `(user_id, role)`。

5. 在**同一个目标 D1** 检查授权是否存在：

   ```sql
   SELECT user_id, role, granted_at
   FROM user_roles
   WHERE user_id = '替换成当前环境的user.id'
     AND role = 'admin';
   ```

6. 刷新论坛并再次打开 `/api/me`，确认 `user.role` 为 `admin`，然后访问 `/#/admin`。服务端每次通过 `user_roles` 查询权限，因此手动 SQL 授权通常不需要退出登录。

### 通过 D1 辅助确认本站用户 ID（可选）

如果手边不方便从网页复制，也可在**目标环境** D1 检查 Google 登录映射：

```sql
SELECT u.id AS user_id, u.nickname, a.provider_subject AS google_sub
FROM auth_identities AS a
JOIN users AS u ON u.id = a.user_id
WHERE a.provider = 'google'
ORDER BY u.created_at DESC;
```

此查询会同时显示 Google 身份标识与本站用户 ID；不要依赖昵称判断账号归属，谨慎核对。

## 方式二：配置 `ADMIN_GOOGLE_SUB`，在 Google 登录时自动授予管理员（自动初始化）

1. 先使用目标 Google 账号登录**目标环境**论坛一次，让该账号写入 `users`、`auth_identities`。
2. 进入对应的 D1 → Console，执行下面的查询获取该账号的 **Google Subject ID**（不是邮箱地址、OAuth Client ID，也不是本站 `users.id`）：

   ```sql
   SELECT u.id AS user_id, u.nickname, a.provider_subject AS google_sub
   FROM auth_identities AS a
   JOIN users AS u ON u.id = a.user_id
   WHERE a.provider = 'google';
   ```

   找到并确认目标账号对应记录，复制 `google_sub`。若用户较多，可以先从 `/api/me` 获取 `user.id`，再在查询中加 `AND u.id = '你的user.id'` 精确筛选。

3. 进入 [Cloudflare Dashboard](https://dash.cloudflare.com/) → 对应的 **Workers & Pages / Worker 项目** → **Settings → Variables and Secrets**。在正确的 **Preview 或 Production** 环境新增或更新 `ADMIN_GOOGLE_SUB`，值为刚才复制的 `google_sub`。建议按环境作为 Secret 维护，不写进 GitHub 源码或公开文档；保存并确认配置已应用到对应部署版本。
4. 该账号**退出论坛后重新通过 Google 登录**。服务端登录流程会比较 Google 令牌里的 `sub` 与环境变量：一致时执行 `INSERT OR IGNORE INTO user_roles(user_id,role) VALUES(?,'admin')`。
5. 重新打开 `/api/me` 验证 `role = admin`；也可以按方式一的验证 SQL 检查 D1。

**重要区别：** 此方法是在 **Google 登录成功时** 授权，而不是在设置变量的瞬间修改 D1。只刷新页面通常不会触发再次授予角色；需重新走 Google 登录流程。一个 `ADMIN_GOOGLE_SUB` 环境变量只对应一个 Google 主体；需要配置其他管理员时使用方式一的 SQL。

## 权限撤销与安全提醒

管理员权限真正存于 `user_roles`，可通过以下 SQL 从**正确环境的 D1**撤销：

```sql
DELETE FROM user_roles
WHERE user_id = '替换成要撤权账号的user.id'
  AND role = 'admin';
```

撤销后再次刷新 `/api/me` 验证 `role`。**如果该用户仍匹配当前 `ADMIN_GOOGLE_SUB`，以后再次 Google 登录又会自动得到 `admin` 权限。** 因此撤销该类账号必须先移除/更新对应环境的 `ADMIN_GOOGLE_SUB`，确认配置已生效，再执行删除 SQL。**仅修改或删除 `ADMIN_GOOGLE_SUB`，不会清除以前已经写入 D1 的管理员角色**。

其他注意事项：

- 只使用站点实际登录产生的有效账户 ID；不要把 `GOOGLE_CLIENT_ID` 或电子邮箱填入 `user_roles.user_id`。
- 不向未核实的账号授予 `admin`；生产 D1 权限修改属于真实运营操作，需要明确授权并核对数据库。
- `moderator` 版主可以由现有管理员在论坛后台的「用户管理」页面授予或撤销；当前页面**不提供直接任命其他 `admin` 的按钮**。
- 如果使用 SQL 手动授权 `admin`，这条操作不会自动经过网站的 `moderation_actions` 审核操作日志；需要自行记录授权对象、环境、时间和原因。
- 两种方式本质上都授予相同的 `user_roles.admin` 角色，**可以并存**，不必二选一。
