# Spine Community — D1 数据库设计 v1 审核报告

> 日期：2026-11-06  
> 审核对象：[设计说明](d1-v1-design.md) 与 [SQL 草案](d1-v1-schema-draft.sql)（审核时 SQL 27 张表、25 个显式索引，blob SHA：3450322efd948ffbc488eb90dcebf71948581963）。  
> **结论：有条件通过逻辑设计，不批准执行正式迁移。** 本报告只做评审和验证，不改变 SQL、网站代码或生产数据库。

## 一、审核范围及结果

- 与[最新业务需求](../开发需求/项目需求总览.md)逐项对照：用户登录、发帖/楼中楼、零至多分类、进展更新、点赞/收藏/关注、跨语言搜索、翻译缓存、审核/申诉、用户隐私、UV/PV/峰值统计。
- 使用独立的本机 SQLite 3.46.1 内存库**重建关键约束的最小可复现模型**并执行写入测试；**尚未用原始 27 表 SQL 全量执行，也未在 Cloudflare D1 环境跑迁移**。
- 通过：父评论不能跨帖引用；进展序号唯一；非根级进展违反 CHECK；已删除主帖可清空正文而继续保留评论；举报不允许同时关联主帖和评论；检查外键无异常。
- 发现：数据库允许“非楼主创建 progress”，作者限制目前只写在设计文档、未成为数据库约束，因此 Worker 的**服务端作者检查必须覆盖创建和编辑**。
- 发现：主帖与评论默认 status 为 pending_review，正常内容在没有额外状态赋值时不会直接公开，违反已定“普通内容先发布后审核”规则。
- 全文检索局部测试：SQLite FTS5 的 unicode61 对“长期腰痛久坐”搜“腰痛”没有命中，trigram 对两字词“腰痛”也没有命中；不能使用简单 tokenizer 就宣称实现中文短词/跨语言搜索。实际部署的 D1 环境仍需专项验证。

## 二、必须在正式迁移前修正（P0）

| 编号 | 问题 | 风险 | 修正建议 |
| --- | --- | --- | --- |
| P0-1 | topics、comments 的默认 status 为 pending_review | 正常新内容被意外隐藏 | 应设计明确的审核状态机：规则判断低风险则 published，中风险 pending_review，高风险 blocked。可以把发布流程统一为 Worker 原子写入显式状态；若保留安全保底默认待审，需**写自动化测试确保正常内容确实公开**，不要只依靠默认值。 |
| P0-2 | **没有真正的全文索引和跨语言检索策略**，只有 taxonomy_aliases | 核心“中文搜到英文相似患者帖子”无法保证，未打标签的帖子会漏搜 | 单列题目/正文关键词搜索、词典概念扩展、中文分词/短词回退、英语词干/同义词、原文索引与排名必须设计为独立检索层；新增可重建索引、版本同步及性能测试。 |
| P0-3 | “楼主才能更新进展”等业务权限只靠应用代码 | 伪造评论可自称楼主进展，或借 API 访问隐藏评论 | Worker 严格校验登录身份、楼主本人、所属主帖、父评论同帖、内容可见状态、角色权限、禁言状态。重要敏感路径加自动化拒绝测试；父评论的跨帖复合外键已经可防部分错误。 |
| P0-4 | 软删除后译文、全文索引、通知预览、页面缓存可能仍存旧文字 | 患者认为已删的健康内容继续泄漏 | 统一“删除状态+清空公开原文+清除译文+搜索去索引+页面缓存失效”的事务/补偿流程；失败可重试并记录；公开 API 永不返回 deleted/hidden 原文。 |
| P0-5 | 旧迁移文件和新草案并存 | 自动迁移可能误执行旧的单分类/日记模式 | 正式迁移创建前审查 wrangler 迁移目录与 D1 当前库状态；明确弃用旧 0001 并清理部署路径里的旧迁移风险；只在**测试库**验证正式 SQL，生产执行需要用户另外授权。 |

## 三、应该在开发实施前确定（P1）

1. **重复状态来源**：users.status 有 banned，user_sanctions 也可以记录 ban；明确唯一的封禁生效来源，避免两边冲突。可以把当前禁言/封禁只由处罚记录推导，users 只表示 active/deleted，或单独维护同步策略。
2. **统计采集链路未定**：4 张聚合表不能自行产生 UV、PV 或五分钟去重用户数；先确定使用 Cloudflare 现有分析能力/边缘采样或隐私友好的去重，再决定存储频率。固定五分钟桶峰值不等同于严格滚动五分钟最高值。PV 不等于 API 请求数；需防刷和费用控制。
3. **Google 站长账号如何安全初始化**：必须明确可信的初始化流程，避免普通注册用户通过客户端自行分配 admin 权限。用户角色撤销要立即生效；Session token_hash 应使用安全、不可逆摘要。
4. **内容计数一致性**：topics.reply_count / like_count 和 comments.like_count 是缓存，点赞/取消、评论发布/隐藏/删除时需事务更新，支持后台对账，不应因为并发出现负数/虚高。
5. **举报重新提交策略**：当前部分唯一索引只防 open/reviewing 的重复举报；已 resolved 后可以再次举报同一内容。是否允许二次举报须在 API 产品策略中说明，不能误称“任何时间最多只能报一次”。
6. **数据约束补足**：topics/comments 的长度上限、source_lang 合法性、progress_seq 与 deleted_at 对应关系、处罚起止时间有效性、public_region 个人自愿提供、通知 comment_id 是否属于 topic_id 等，按已确认需求+实现评审确定。不要将不完整的字段范围当作用户已定的业务门槛。
7. **分类术语**：taxonomy_terms.term_type='region' 容易与用户公开地区混淆，建议改成 body_part，症状、治疗、栏目独立维度并允许一个帖子关联多类词条。
8. **费用上限**：translation_usage_daily 能做报表，但不能单独保证第三方翻译不会在并发下超额。需要原子额度预留/速率限制/强制熔断，失败时回退原文。
9. **站内通知**：event_key 去重策略与取消后重新点赞、申诉结果等事件的区别，以及隐藏帖子通知的可见性判断，需要补充。避免通知文案复制被删除的健康原文。
10. **未来账号注销**：不能直接 CASCADE 删除用户及全部帖子/第三方评论。保留匿名占位与最少必要审计关系，但数据保留政策/合法申诉期限需上线前决定。

## 四、Cloudflare D1 的具体注意事项

- 官方文档确认 D1 默认启用外键约束，用户查询中无法把它永久切为 OFF；SQL 顶部的 PRAGMA foreign_keys = ON 在 D1 中**没有必要**，正式迁移建议删去，并按 D1 要求使用 defer_foreign_keys 做必要迁移。参见 https://developers.cloudflare.com/d1/sql-api/foreign-keys/ 。
- D1 支持 SQLite FTS5，但这**不等于跨语言语义搜索已经实现**；中文短词召回需要专门方案。参见 https://developers.cloudflare.com/d1/sql-api/sql-statements/ 。
- 官方文档说明包含 FTS5 虚拟表的数据库导出有限制。若采用 FTS5，索引应可由原文重建，提前设计数据备份/导出恢复流程。参见 https://developers.cloudflare.com/d1/best-practices/import-export-data/ 。
- 这次本机测试是**关键约束抽样验证**，不是完整原始 SQL 在 D1 的兼容性认证。下一步必须执行全量 DDL、外键检查、索引计划和删除/账号注销集成测试。

## 五、审核结论与下一步

- **设计方向：通过。** 27 张表按业务分组不是天然过度设计；第一阶段只需用户、身份、分类、帖子及评论等基础表，后续按模块启用。
- **迁移/上线放行：暂缓。** P0-1、P0-2、P0-3、P0-4、P0-5 在编码和正式迁移之前修正/验证。
- **建议下一步：** 先修订 SQL 草案和设计说明，再在隔离 D1 测试环境全量运行并验证 CRUD/删除/禁言/跨语言关键词/统计；通过后再产出正式迁移文件。**本审核不授权修改生产数据库、运行 migrations 或修改 Worker 代码。**
