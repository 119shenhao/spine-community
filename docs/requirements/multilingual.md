# 多语言与自动翻译需求（讨论稿 v0.2）

> 最近决定：2026-11-06。仅需求设计；无翻译功能上线、无翻译 API 账号配置、无数据库表已创建之声明。

## A. 已确认的用户体验

1. **共享全球社区**：七种语言共用帖子、回复、账号与后台，不分七个独立论坛。
2. **首访语言**：依据浏览器偏好选择初始界面语言；用户可手动切换并记住选择。用户的主动选择优先。
3. **七种界面语言（首版目标）**：英语 `en`、简体中文 `zh-CN`、西班牙语 `es`、巴西葡萄牙语 `pt-BR`、德语 `de`、法语 `fr`、日语 `ja`。这些是初始建议的语言代码，地区细节可调整；未来可增加印尼语、俄语等。
4. **发帖／回复原文（已确认）**：用户可使用任何语言发布帖子或回复；系统必须永久保留用户实际提交的原文并记录其原始语言，所有自动翻译结果均单独保存为译文缓存，绝不覆盖原文。
5. **自动翻译默认开启**：阅读者直接看到自己所选语言的外语帖内容，原文不需要另行翻译；在同一帖子里，多语言回复也能相互理解。
6. **原文随时可查**：提供“查看原文／查看翻译”切换，标注“机器翻译”，尤其提醒药物名称、剂量和诊断术语可能错误。

## B. 已同意的成本节约原则

采用“**自动呈现 + 按需生成 + 持久缓存**”，不是把所有帖子提前批量翻成七种语言。

- 首页／列表：只处理当前展示的标题和摘要，不预翻译全部历史内容。
- 详情页：访问时翻译正文；回复按当前显示的范围／分页处理，不一次翻译所有历史回复。
- 首次需要该目标语言且无有效缓存时，Worker 请求第三方翻译服务，并将译文存入 D1；下一位使用相同语言的读者直接读取缓存。
- 同一源内容被编辑后，旧译文应失效或标记为过期，避免展示与原文不一致的医学信息。
- 同一内容相同语言的并发请求应尽可能合并，防止并发重复付费。
- 设置服务端每日／每月限额、字符上限、频率限制及费用熔断；不允许无限刷接口。
- 翻译失败或达到限额：显示原文并标注原因，不隐藏帖子，不虚构译文。
- 界面文案翻译可以随代码维护，与需要持续 API 调用的用户内容翻译分开。

## C. 服务选择（**建议，未定稿**）

- 当前倾向：Microsoft Azure Translator 的免费套餐作为候选；此前讨论过其按字符计费及免费额度。
- 尚未批准创建第三方付费账户／密钥、升级计费套餐或自动充值；**不能把价格或免费额度视为永久保证**，接入前必须重新核对供应商规则和可用地区。
- 需要确认：第三方隐私条款、医疗相关敏感内容能否传输、合规地区、数据保留、访问限制、真实硬性用量控制。

## D. 安全、隐私和健康内容

- 翻译只针对符合论坛公开权限的内容；**不得把私密草稿、未授权内容传给外部翻译 API**。
- 公开前做好隐私说明：哪些正文会送往第三方翻译、第三方用途与保留政策、如何避免披露身份信息。
- 不能把自动翻译当成医学审校；对数字、药物单位、否定词等高风险内容保留一键原文核对。
- 若用户原语言与阅读语言相同，直接显示原文，不产生内容翻译调用。

## E. SEO 与查找（方案待讨论）

- 规划语言路径，例如 `/en/`、`/zh-cn/`、`/es/`、`/pt-br/` 等；实现方式、slug、canonical 与 hreflang 仍待讨论。
- 不应自动将所有未经人工质量检查的机器翻译页面都开放搜索引擎收录；优先考虑少量高质量公开索引页面。
- **已确认（2026-11-06）**：默认检索全球所有语言的公开帖子，读者所选界面语言决定默认译文展示而非限定原帖语言；默认“最相关”，可切换“最新”“讨论最多”。跨语言症状概念、原文全文搜索与关键词扩展应共同参与，不能依赖按需生成的译文缓存已经存在。详情参见 [症状搜索需求](search.md)。

## F. 未来数据结构需要预留（**非已批准建表方案**）

- 用户语言偏好（以及用户明确选择记录）；
- 帖子／回复原文、原文语言、正文版本；
- 译文对应的内容 ID、语言、原文版本、翻译来源、生成时间；
- 翻译服务用量统计／限流信息；
- 公开／私密权限检查与被删内容缓存清理。

具体建表和字段要在全部产品需求确认后再评审；现阶段不得运行迁移。
