# Spine Community — AI 采集前必读流程（多 AI 去重）

**文档位置：main/docs/ai-collector-sop.md。** 适用于 DeepSeek、ChatGPT、Claude、Codex 及其他采集程序。目标是将获得适当使用权限的颈椎、腰椎讨论内容导入**独立开发数据库**，不触碰生产库。

**开始搜索之前，必须阅读本文和 [采集协调接口](collection-api.md)。** 不能真正访问 HTTPS 接口的普通聊天 AI，须交给具备 HTTP 能力的工具执行，不能声称已经认领或导入。

## 总流程

```text
AI 启动
  ↓
GET /api/collect/exclusions?site=tieba
  分页获取「已完成」和「其他 AI 正在采集」的帖子 ID
  ↓
AI 搜索贴吧，解析搜索结果中的帖子 ID
  ↓
先在本地排除清单中过滤，旧帖不用打开正文
  ↓
POST /api/collect/claim
  同时申请最多 30 个候选 ID 的采集权
  ├─ completed / in_progress → 跳过
  └─ granted → 保存对应的 lease_token 和到期时间
       ↓
       只采集 granted 的原始正文、回帖、楼中楼
       ↓
       POST /api/collect/complete
       一笔数据库事务：核验采集权 → 主帖内容指纹去重
                        → 首次写主帖和回复 → 完成采集记录
       ↓
       下个 AI 再拉清单，能立即看到刚完成的 ID
```

## 1. 搜索前：下载完整排除清单

**无需密钥、Cookie 或登录**，直接调用 `GET /api/collect/exclusions?site=tieba&limit=200`。如果 `next_cursor` 不为空，要继续翻页直至为空，不能只拿第一页。

- `completed`：已采集，永久排除。包括原站 ID 与已有正文重复、最终未再次发帖的情况。
- `claimed`：其他 AI 临时认领，暂时排除。响应有 `lease_expires_at`，锁过期后刷新列表再判断。

**搜索引擎不一定能排除几千个链接。** 所谓“搜索时过滤”是：先尽量优化查询；搜索结果出现后解析候选 URL 中的帖子 ID，**在打开完整帖子及评论页面之前**先用本地清单排除。清单会变化，不能只依赖上次下载的版本。

每轮新搜索开始时重新获取排除清单（至少刷新候选前的状态）。

## 2. 搜到候选编号后：申请采集权

不要急着读取帖子正文、全部楼层。先把候选 ID 批量发给 `POST /api/collect/claim`。

示例：贴吧链接 `https://tieba.baidu.com/p/123456789`，其 `site=tieba`、`source_id=123456789`。Reddit 使用帖子原站的稳定小写 ID，而不是整条 URL。内部记录按 `(site,source_id)` 唯一。

- 只有返回 `granted` 才能开始深度采集，服务端返回独立的 `lease_token`。
- 同一站点、同一帖子 ID 的并发认领通过数据库原子写保证最多只有一个成功。
- 租约为 **21600 秒（6 小时）**，没有续租接口。采集时间超过 6 小时时须重新认领，旧令牌失效；采集完成应尽快提交，不必等待期限结束。

## 3. 深度采集：保持原语言及层级

拿到采集权后才访问原帖和回帖，采集过程尊重原站条款、作者许可、访问频率和隐私。不能未经许可批量转载受著作权保护的整篇帖子或完整评论，不能把外部患者的经验伪装为本站真实用户原创。如果只是信息整理，需明确整理性质与来源，在可合法使用的范围内导入。

每篇主帖和每条回帖都保留实际原文语种：英文标 `en`，中文标 `zh-CN`，楼中楼继续使用 `replies` 维护父子关系。不预先把英文翻译成中文入库。**不要擅自在正文中添加“开发测试”“开发预览”等说明；也不要编造患者的亲身经历。**

每次 `complete` 只提交一篇主帖及至多 49 条回复，总体请求体不超过 150KB，回复层级不超过 8 层。超过限制需要合法、明确地分批安排其他内容；接口故意不支持已完成主帖的回帖增量追加，所以**不要假装截断的评论已经全量导入**。

## 4. 完成导入：一次完成去重和采集记录

把 `site`、`source_id`、`lease_token`、`topic` 提交到 `POST /api/collect/complete`。

服务器事务内检查令牌是否仍有效、查内容指纹，若找到与其他原帖一样的主帖正文，则**只标记新的原站 ID 为已处理并关联已有帖子**，不重复创建帖子和评论。否则新建主帖及当前完整的评论树，并更新采集状态为 `completed`。事务失败则两者一起回滚。

同一令牌和同一正文重试已完成请求是安全的（返回 `already_completed=true`）；换了正文则拒绝，避免把错误数据算成功。下一次任何 AI 获取 exclusions 时，这个原站 ID 已出现在 completed 清单中。

## 5. 异常和失败重试

采集不可继续时立即调用 `POST /api/collect/release` 释放自己的租约；若任务突然退出，租约也会在 6 小时后自动失效。

遇到 `claim_not_owned_or_expired`：返回候选阶段重新认领。遇到 `in_progress`：跳过，不抢占别人的未过期锁。遇到 `completed`：跳过，不追加该主帖的新回复。遇到数据库错误：不要宣称已完成，保留本地草稿，在租约有效期内按原 token 重试。

**采集协调不等于生产发布。** 采集记录只在开发 D1；开发库→生产库继续按[主帖一次性同步](topic-dedup-and-sync.md)执行，先审核再同步。

旧的 `/api/import/topics` 或 `/api/import/batch` 如果没有提供原站 ID，就无法自动生成采集排除清单；它们仍有正文指纹去重。今后多个 AI 协作采集，应全部使用 `claim → complete`，不要绕过采集权直接调用旧接口。

## 6. AI 执行时应记录的结果

每轮仅在自己的私有任务记录里保存：来源站点、候选 ID 数、排除数、成功认领数、完成数、正文重复数、失败数与需要重试的 ID。认领令牌仍是临时敏感信息（用于防止其他 AI 完成或释放你的采集任务），不应写进公开仓库或日志。

**注意：** 采集 API 现为**开发预览环境免密接口**，可以直接用 HTTP 调用；生产环境仍禁止这些接口。任何知道预览地址的人也可能占用采集位或提交内容，因此继续保留限流、认领令牌、原站 ID 和主帖内容指纹约束。完整字段、错误码与示例见 [collection-api.md](collection-api.md)。

## 给其他 AI 的启动指令（可复制）

> 开始任何搜索前，先打开 GitHub 仓库 `119shenhao/spine-community` 的 `main/docs/ai-collector-sop.md` 和 `main/docs/collection-api.md`。先向预览服务器分页拉取 exclusions；找到搜索结果 ID 后先本地过滤，再批量 claim；只采集 granted 的公开且获授权内容，保留原语种及楼中楼结构；采集完立即 complete，失败 release。不得绕过接口的认领、正文指纹与数据库约束，不能向生产数据库写入，也不能把没有执行过的请求说成成功。


## ChatGPT 统一采集指令（2026-11-08 已确认）

**用户标准指令：`执行采集贴子任务`。** `执行采集帖子任务` 为同义表述，含义一致。用户说这句话，即表示要求**当次立即触发一次已有站点的采集工作流**；不需要逐站报出名字，也不要求用户手动点击 GitHub Actions 的 Run workflow。不等于创建每天自动运行的定时任务；定时调用必须另设定时计划。

- GitHub 私有仓库：`119shenhao/spine-community`，采集代码位于开发分支 `feature/v1-community-build-20261106`，执行入口是 `scripts/spine_collect.py`；工作流 `.github/workflows/spine-collector-on-demand.yml` 监听 `.github/spine-collector-request.json` 的提交。
- 每次收到该指令，ChatGPT **通过 GitHub 连接器**读取最新程序和登记的来源后，将配置文件写为 `mode:"collect"`、`sites:["all"]`、`candidates:{}`、`limit:10`，并写入**唯一**的 `request_id`（不能重用上一次），提交开发分支。无需也不得因此编辑生产分支的工作流或触碰生产 D1。
- `sites:["all"]` 由 `read_request()` 在 **GitHub Actions 执行当时**展开成 `scripts/spine_sources.py::SOURCE_URLS` 当前登记的全部站点；**不固定为六个**。未来新增获合法授权且已经完整接入解析、发现、测试及服务端来源校验的网站时，只需注册到站点表，后续统一指令会自动包含它。不承诺未开发/未授权的任意新站可以自动抓取。
- 默认目标为一次合计**最多新增10篇主帖**，不是每个网站10篇；按注册顺序轮流查找，达到目标后停止，因此不保证每轮都访问完所有已登记网站。若用户指定数量、站点或别的条件，则本轮以用户明确参数为准，不永久改默认值。
- GitHub Actions 会按需安装 Python 与访问来源所需依赖，采集结果只写开发预览 D1；按既有排除清单、租约、去重、内容校验、长帖暂存和原子入库规则执行。未达到目标应报告真实数量，不能制造或重复帖子来凑数。
- 提交后应确认该次 GitHub Actions 确实启动，尽可能核验已完成的运行日志，并报告运行链接、各站候选/新增帖子及回复数量、重复、失败、未达标原因。若工作流尚未结束，要明确说明正在运行，**不能提前宣称采集成功，也不能承诺在后台稍后主动送达报告**。
- **不要在用户只是讨论如何调用、询问可行性、修改采集规则时自动启动采集。** 只有明确的“执行”指令才触发。
  
统一配置示例（仅展示，不代表本次执行）：

```json
{
  "request_id": "collect-all-unique-id-per-run",
  "mode": "collect",
  "sites": ["all"],
  "candidates": {},
  "limit": 10
}
```

调用之前仍需遵守本文其他授权、去重、隐私、频率和开发/生产隔离约束。
