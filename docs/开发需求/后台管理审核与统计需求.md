# 后台管理、举报审核、操作日志与统计需求

> 讨论日期：2026-11-06。**仅产品需求记录，未开发、未建表、未部署。** 本文区分已确认的方向和待设计的实现细节。

## 一、内容发布与自动防垃圾（已确认）

- 正常患者帖子、评论 **先发布，后审核**；不要求每篇文章经过管理员审核后才公开。
- 可疑垃圾内容优先使用 **规则识别 + 人工复核**，首版不依赖付费 AI 审核。识别信号包括：广告和商业引流、重复内容、可疑链接、短时间高频发帖或批量提交等。不能仅因出现药物名称、康复方法或不同医疗观点就判定广告／违规。
- **三级处理**：
  1. 低风险：直接公开。
  2. 中风险：保存为“待审核”，作者本人可查看状态，其他人暂不可见，管理员批准后直接公开，无需重新发帖。
  3. 高风险：规则自动阻止发布并记录原因，提供复核／申诉途径。
- 具体规则、阈值、误报纠正、防刷限流、重复内容识别、链接黑名单、是否引入 Turnstile 等留待实现设计；风险评分不能替代对复杂医疗争议的人工判断。

## 二、用户举报流程（已确认）

- 登录用户可举报**帖子或评论**，通过内容菜单选择原因，可选填说明；游客只能浏览公开内容，不可提交举报。
- 举报原因首版建议：广告／垃圾信息、诈骗或虚假医疗宣传、辱骂骚扰或歧视、个人隐私泄露、可能造成伤害的医疗建议、其他。原因名称和更细选项可在界面设计时调整。
- 每位用户对同一条内容**最多一条有效举报**，防止重复举报刷数量；系统保存举报人内部 ID、内容稳定 ID、原因、时间与状态。举报人身份不向被举报人公开。
- 举报进入管理后台待审队列，**默认不因有人举报就直接删除或隐藏**。严重风险优先排队处理。
- **已确认：即使十个人或更多人举报，也不只凭人数自动隐藏**；举报数可以提升审核优先级，但需要结合内容风险判断，以免恶意集体举报造成误伤。与第一节的规则识别高风险自动拦截是两种不同机制。
- 管理员可以决定保留、隐藏、恢复或按权限删除内容，必要时处理账号；操作记录处理人、时间、内容、措施和原因。应允许当事人申请复核／申诉。
- 对举报人反馈处理结果可使用站内通知；具体通知颗粒度、公开哪些审核细节及申诉期限留待讨论。
- 医学观点有争议不等于违规；审核应重点考虑垃圾广告、骚扰、隐私与实际安全风险。

## 三、后台角色与权限（已确认）

- 首版**设计两级角色：站长、版主**；上线初期可以仅启用站长账号。后续需要时任命志愿者版主，不必一开始招聘。
- 站长：管理举报、隐藏／恢复／删除内容、临时禁言和永久封禁、管理分类与症状标签、任命／撤销版主、调整系统设置、查看管理日志和统计。
- 版主：审核举报、隐藏／恢复内容、执行**临时禁言**；不能永久封禁、永久删除、任命版主、修改系统设置或分类标签。后台日志和统计可以按必要范围开放只读权限。
- 版主临时禁言时长：**1 天、3 天、7 天、30 天** 四种固定选项；永久封禁只能由站长操作。临时禁言的具体禁止行为与提前解禁方式在实现前细化。
- 管理员**不能擅自修改患者原帖正文**；处理方式是审核、隐藏、恢复或删除。版主不应看到 Google 邮箱、登录凭证等不必要的私人账号信息。
- 后台与每个敏感操作必须由**服务端做角色授权**，不能只靠界面隐藏按钮；权限变更须及时生效，站长可以撤销版主权限。
- 第一版不按语言或国家限制版主只能审核某一组帖子；未来可以有工作分工，但论坛可能出现多语言混合讨论。

## 四、后台操作日志（已确认）

- 至少记录：**操作管理员、操作时间、对象（帖子／评论／用户等）、操作类型、处理理由**；方便复盘误判和安全问题。
- 管理员可检索／查看相应日志。日志只向有权限者开放，不对普通用户公开。
- 日志保留多久、是否需要导出、哪些安全事件额外记录，以及日志中个人信息最小化策略，待后续技术和合规评审。

## 五、第一版基础统计（已确认）

- **按天汇总的社区数据**：注册人数、发帖数、评论数、举报数；首版以简洁列表／小图表为主，不做大型实时可视化后台。
- **按天汇总的四项流量数据**：
  1. 每日独立访客 **UV**（当天访问网站的去重访客，包含未登录游客；具体隐私友好的去重方法待定）。
  2. 每日页面浏览量 **PV**（用户访问的页面查看次数；不能简单等同 API 请求数）。
  3. 每日**最高同时活跃人数估计值**，建议用滚动最近五分钟内的独立活跃访客数近似，明确标记“估算”，不声称是瞬时精确并发。
  4. 每日**小时访问量峰值**：全天各小时 PV 中的最大值及发生的小时，区别于最高同时活跃人数。
- 支持查看最近 **7 天／30 天** 趋势；峰值记录时间，统计时尽量排除机器人与内部异常流量。
- **第一版不做按国家分组的流量统计**；未来需要时再讨论。也不要求按语言或分类分别统计。
- 数据口径（访客去重、访问活跃判定、时区、采样精度）、性能与免费额度保护属于实现阶段需补充的技术决策，不能假设 Cloudflare 自动提供完全准确的上述全部指标。

## 六、范围与尚未确定事项

- 本次确定的是首版后台业务方向，**不是已上线的功能**。
- 首版不做复杂审核 AI、复杂权限等级、按国家统计或实时大屏。
- 具体防刷阈值、后台审核列表 UI、举报通知文案、日志保留期限、统计采集方案与安全合规仍待技术设计。
- 需求讨论期仅修改 `docs/` 中的文档，不改 Worker、前端、Cloudflare 配置，不创建或迁移 D1 表。

## 七、流量统计改为社区管理后台开关（2026-11-10 用户确认）

- **产品决定**：流量统计由站长在「社区管理 → 社区统计」直接开启或关闭；不依赖 Cloudflare 设置 `ANALYTICS_SALT` 或第三方统计服务。生产/预览沿用各自独立的 D1。
- **默认关闭**：已有 `settings` 表中的 `analytics_enabled` 项不存在或不等于 `true` 时视为关闭。站长在后台切换后使用 UPSERT 持久化，设置变更记入 `moderation_actions` 审计日志；版主可以查看数据但不得更改开关。
- **关闭行为**：前端在健康检查返回关闭时不发出新的 `POST /api/pageview`；即使手工请求统计接口，服务端也必须在写入统计表前检查 D1 开关，返回 `{ok:true,recorded:false,reason:'analytics_disabled'}`。原有用户/帖子/回复/举报等社区业务统计继续有效。
- **开启行为**：页面浏览后记录 PV、UV 估值、五分钟活跃峰值和小时峰值；匿名访客用随机生成的 256 位 `sc_visitor` Cookie 去重，仅保存按 UTC 日期隔离的哈希，不保存明文 Cookie。已记录的历史统计不因关闭而删除。
- **资源与安全**：沿用 `/api/pageview` 现有限流、机器人过滤；不增加付费依赖。当前统计写入会增加 D1 负载，若浏览量扩大应优化聚合并增设更严格配额保护。
- **接口**：已有 `POST /api/admin/settings` 允许站长设置 `{key:'analytics_enabled',value:'true'|'false',reason:'...'}`；`GET /api/admin/overview` 返回 `analyticsEnabled`，`GET /api/health` 返回 `analyticsEnabled` 和兼容别名 `analyticsConfigured`。
- **开发与发布状态**：代码先在 `feature/v1-community-build-20261106` 实现和验证，生产版 `main` 的程序代码尚未因此更新；本节是已确认的产品需求与实现目标，不意味着生产环境已开启。

## 八、全站当前帖子与评论总量（2026-11-12 用户确认）

### 已确认需求

- 在「社区管理 → 社区统计」新增「全站帖子总数」「全站评论总数」。
- 统计本环境当前实际存在的已发布内容，包含用户发布与采集导入；排除草稿、已删除及未公开内容。开发和生产分别读取各自数据，不跨环境相加。
- 主帖每篇只计入帖子总数，不计入评论总数。
- 评论总数包含普通评论及各级楼中楼，每条实际回复只计一次，不因父子关联或联表重复计数。
- 用户明确确认示例：一条评论下面有三条楼中楼，合计 **4 条评论**，不是 1 条；其主帖另计 1 篇帖子。
- 新增总量代表当前存量，不随最近 7 天／30 天筛选变化；原有期间新增数据需使用准确名称与总量区分。

### 现有实现核实（代码检查，非线上实测）

2026-11-12 检查 main 与开发分支的 public/app.js、src/admin.ts：

- 社区统计的帖子、评论卡片分别累加 overview 返回的 new_topics、new_comments，默认最近 7 天，可切换最近 30 天。
- 后端按 UTC 日期读取 daily_community_metrics，没有按当前管理员 author_id 过滤。因此这些数字是全站期间记录的新增量，不是管理员个人数量，也不是直接查询当前内容表得到的存量。
- 帖子卡片和表头复用了 myTopics 翻译键，中文显示「我的帖子」，造成误解；应改为「期间新增帖子」，评论对应「期间新增评论」。
- 新增计数完整性（导入／同步路径、删除是否回退等）尚未全部审计，不能把期间计数当作当前有效内容总数。

### 验收与状态

- 用 1 篇已发布主帖、1 条普通评论、3 条楼中楼验证：帖子总数增加 1，评论总数增加 4。
- 切换 7 天／30 天不改变当前总量；不同管理员查看同一环境时总量一致。
- 以当前数据库已发布内容核对，确认采集导入被包含、删除内容被排除；查询必须服务端验证后台权限。

## 九、按来源分别统计帖子和评论（2026-11-12 用户确认）

### 来源分类

统计分为两类，同时适用于当前总量和期间新增统计：

| 来源分类 | 包含范围 | 帖子指标 | 评论指标 |
| --- | --- | --- | --- |
| 导入内容 | 采集入库、导入接口、开发环境同步到生产环境 | 导入帖子数 | 导入评论数 |
| 用户发布内容 | 用户通过前台页面实际发布的主帖与回复 | 用户发布帖子数 | 用户发布评论数 |

- 全站当前帖子总数、评论总数保留，并分别展示上述两类来源的数量。
- 来源按每篇主帖、每条评论自身的实际写入途径判断，不按父帖来源判断；例如用户在导入主帖下通过前台回复，该回复计入用户发布评论。
- 普通评论与楼中楼都按各自来源逐条统计，一条评论加三条楼中楼合计四条。
- 「导入」包含同步至生产的内容；不将采集与同步拆成两个用户要求的顶层来源类别。
- 每条内容在同一环境仅计一次；去重命中、同步重试或导入请求重放不得增加计数。
- 当前总量仍只统计当前有效已发布内容，排除草稿、已删除及未公开内容；开发与生产分别统计。
- 完成历史来源核实后，应满足：全站帖子总数＝导入帖子数＋用户发布帖子数，评论同理。历史来源无法可靠确认时需明确标注待核实数量，不能仅凭昵称 Anonymous 武断归类或伪造二分结果。

### 已核实的现状与开发调整计划

- 现有前台发布代码调用新增计数；src/import.ts 与 src/collect.ts 同样更新 daily_community_metrics 的 new_topics、new_comments，采集及接口导入按入库当日 UTC 计数。
- 已检查的 scripts/sync-preview-to-production.mjs 写入帖子和评论，但没有更新该每日计数。因此现有期间新增统计并未完整覆盖生产同步来源；这不是纯前台发布量。
- 开发时先核实并持久化每条内容的来源，检查历史采集、导入与同步记录，制定可验证的历史回填方案；不能使用作者昵称作为唯一来源证据。
- 新增全站当前存量与两类来源分项；同时将 7 天／30 天新增数据按两类来源拆分。期间统计按本环境实际首次新增入库时间记录；同步不得以原帖历史创建时间冒充本环境入库时间。
- 将误用的「我的帖子」等个人文案改为准确的期间统计名称；分别显示「期间新增导入帖子／评论」「期间新增用户发布帖子／评论」，避免与当前总量混淆。
- 统一前台、采集、导入接口、生产同步各路径的统计规则及幂等处理，补足同步来源计数；来源及统计修改应沿用已有流程。
- 开发代码在开发分支实现和验证，文档保留在 main/docs；生产部署属于后续发布步骤。

### 验收

- 导入一篇帖子及四条回复：导入帖子增加 1、导入评论增加 4，用户发布分项不增加。
- 前台发布一篇帖子及回复：仅增加相应用户发布分项。
- 前台用户在导入帖下回复：计入用户发布评论。
- 同一帖子同步重试不重复计数；生产同步内容计入生产导入分项。
- 当前总量与按来源分项核对一致，7 天／30 天切换不改变当前总量；期间分项按实际本环境入库日期核对。
- 本节为已确认开发需求；**2026-11-12 已完成开发实现、本地测试与预览构建，生产未发布**。
