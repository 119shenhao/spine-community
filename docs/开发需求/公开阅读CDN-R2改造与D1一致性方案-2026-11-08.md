# Spine Community — 公开阅读 CDN + R2 分流与 D1 最终一致性改造需求

> 日期：2026-11-08
> 状态：**开发需求／技术实施方案；尚未开发、尚未部署**
> 项目：`119shenhao/spine-community`
> 执行方式：交给 Codex / ChatGPT Work 进行开发分支实施和预览验证。
> **授权边界：本文件的提交仅限 `main/docs/`；不代表授权创建付费资源、修改生产 D1、变更生产域名、发布生产 Worker 或部署生产 Cron。**
> 关联规范：[开发与发布规范](../development-release-workflow.md) · [需求主文档](../requirements/README.md) · [文档总导航](../README.md)

## 一、目标与不可妥协的原则

1. **主要目标：尽量节省 Cloudflare Workers Free 每日 100,000 次请求配额**。公开、匿名的帖子列表、帖子正文、公开回复等高频读取，不再每次执行 Worker、查询 D1；改从 Cloudflare CDN → R2 自定义域名公开读取 JSON。
2. **写操作仍走 Worker + D1**：发帖、回复、编辑、点赞、收藏、关注、登录、审核与通知等仍由服务端鉴权并处理，不因“静态化”降低安全性。
3. **D1 是唯一权威数据源，R2 是可重建的公开投影，CDN 是可丢弃缓存**。任何情况下不可把 R2 / CDN 当作权威用户数据。
4. **兼容现有功能**：搜索、筛选、20 条一页列表、50 条一页回复、楼中楼、楼主进展、多语言显示与查看原文、Google 登录、点赞收藏/关注及通知、审核、删帖占位与隐私请求都不能退化。
5. **所有用户私有数据绝对不能进入公开 R2 JSON**：不包含 Google 身份、邮箱、会话/令牌、私人收藏与关注关系、未公开地区、内部审核理由、未发布内容、原始导入来源链接等。
6. **先开发环境验证，后单独申请生产批准**。上线前必须完成性能、并发、失败、隐私/删除、费用和回滚测试；禁止直接改生产部署或数据。
7. **成本受控**：不要为了每次点赞或每次浏览重建 JSON；限制同步频率、批量大小、读写量和缓存清理调用数量；资源开通前先核实 Free 套餐与实际账单/配额。

## 二、已核对的仓库现状（2026-11-08，main 快照；Codex 开工后须重新核对开发分支）

- `wrangler.jsonc`：`main=src/index.ts`，Static Assets 目录 `./public`；`assets.run_worker_first` 当前包含 `/api/*`、`/`、`/index.html`；生产 `DB` 与 Preview `DB` 使用不同 D1。
- `src/index.ts`：HTTP Worker 负责 `/api/*`，非 API 由 `env.ASSETS.fetch` 处理；`/` 和 `/index.html` 目前经 Worker 在 Preview 响应写入 `X-Robots-Tag: noindex, nofollow`。
- `src/search.ts`：`GET /api/topics` 和 `GET /api/search` 动态 D1 查询；有筛选、相关度与分页，不能不加区分地把所有查询变成同一份缓存。
- `src/content.ts`：`GET /api/topics/:id` 返回帖子、公开/权限相关回复、进展与分页；`POST /api/topics`、`POST /api/topics/:id/comments`、编辑/删除与互动会修改公开数据。
- `src/community.ts`：`GET /api/me`、`GET /api/me/content`、通知与 `POST /api/pageview` 仍会消耗 Worker；即使公开内容迁到 R2，也不能宣称“打开页面零 Worker”，除非实际网络请求验证如此。
- `public/app.js`：首页通过 `/api/topics?...` 载入列表，详情通过 `/api/topics/:id` 载入正文/回复；需改成公开数据与个人状态的拆分读取，并保持现有不刷新全页的交互。
- `src/admin.ts`、`src/import.ts`、`src/collect.ts`、翻译与隐私相关路径同样可能改变公开帖子；必须纳入投影更新覆盖范围。
- **重要：当前“同步帖子从开发到生产”并不经过 HTTP 发帖接口！** 已核对 `main/scripts/sync-preview-to-production.mjs`，它通过 `wrangler d1 execute --remote` / SQL 文件直接向生产 D1 写入主帖、评论和标签；`.github/workflows/sync-posts.yml` 调用该脚本并将脚本锁定在已验证的 commit `4580263f1ec66feed1d1f2d2722873068455f2bb`。因此**仅修改 Worker 的普通发帖 / 采集接口不会触发生产 R2 更新**。
- 现有“开发帖同步到生产”仍然是**独立的跨环境业务数据同步**；新的 D1→R2 投影仅发生在**各自环境内部**：① 采集 API 写 Preview D1 → 更新 Preview R2；② 发布脚本写 Production D1 → 更新 Production R2。两个同步机制不合并、不交叉写桶，也不得改写“已同步帖子不再增量同步回复”的既定规则。
- **必须修订/升级生产同步脚本及其 GitHub Actions 锁定代码机制**：推荐在生产帖/回复 SQL 写入的同一事务内记录对应的公开投影 outbox（也可评估经过验证的 D1 触发器），随后由生产同步处理器发布 R2 和清理 CDN。不可只在 SQL 成功后临时调用一个无持久记录的刷新 API，否则脚本崩溃会留下永久未同步的数据。脚本改造后先进行专门审计与测试、更新固定 SHA/工作流并获得该流程所需的生产授权；不要直接解除旧脚本锁定保护。

## 三、目标架构与域名

```text
匿名浏览器
  ├─ 网站域名（示例：www.example.com）
  │    ├─ HTML / CSS / JS：Workers Static Assets，直接静态返回
  │    └─ 写入、登录、个人状态、动态搜索等：Worker → 本环境 D1
  └─ 公开数据域名（示例：data.example.com，R2 Custom Domain）
       └─ Cloudflare CDN Cache
            ├─ HIT：返回公开 JSON，不运行论坛 Worker
            └─ MISS：读取同一环境 R2 对象，不运行论坛 Worker

写入：Worker → D1（业务写入 + 投影版本 + 待同步任务，在同一 D1 事务）
                 └─ 同步处理器 → 读取 D1 最新公开数据 → R2 JSON → CDN Purge
定期补救：生产 Cron Trigger → 处理 D1 待同步任务、失败重试与告警（不扫描 R2；批量对账暂缓）
```

- 域名仅作示例；需**用户拥有并接入 Cloudflare 管理的域名**，通过 R2 Custom Domain 连接公开桶。现有 `workers.dev` 域名本身不能直接当成 R2 自定义 CDN 域名。
- `data.example.com` 不可添加会执行论坛 Worker 的路由；验收时以 Worker 指标与请求实测证明匿名公开内容读取不会进入 Worker。
- 为 JSON 单独配置 Cache Rule，限制仅 `GET/HEAD` 公共对象；不要缓存带用户 Cookie/Authorization 的个性化响应。
- 配置 **R2 CORS** 允许论坛站点的确切 Origin 以 GET 读取；单独验证 Preview、Production，不用泛化的公开写权限。
- **开发、生产使用独立 R2 桶、独立 D1、独立地址/命名空间和独立绑定**。预览阶段可先通过 Preview 绑定验证生成及读取；若尚未配置独立预览 CDN 域名，不得伪称真实 CDN 命中与不计费路径已经验收。不得用开发流程写生产 R2。

## 四、公开 JSON 范围与格式

### 4.1 应优先静态化（第一阶段）

- 匿名首页“最新公开帖子”第一页及后续标准分页；只包含公开、已发布的帖子（或符合既有“已删除占位”规则的最小占位）。
- 每篇公开帖子的标题、正文、公开作者昵称及用户明确公开的地区、原始语言、公开标签、时间、可公开计数。
- 公开回复、楼中楼关系、楼主进展及其分页；沿用当前排序、定位特定回复和回复深度逻辑。
- 版块/公开分类等低频公共数据可作为后续候选；先以减轻最大流量路径为优先。

### 4.2 保留 Worker 处理（至少第一阶段）

- 发帖、回复、编辑、删除、点赞、收藏、关注、举报、审核、Google 登录、个人中心、通知、我的收藏/关注状态、用户自身未公开内容及权限校验。
- 带关键词的搜索、复杂筛选、相似结果、跨语言检索等优先保持现有 D1/Worker 实现；可择优后续静态化**无个人信息、参数明确、访问量大的标准列表**，不得破坏结果正确性。
- 多语言翻译需要尊重当前“访客首选语言自动显示 + 查看原文”规则。公开 JSON 保留原文、原语种；仅公开已经核准可展示的翻译。翻译服务调用、个人偏好判定仍可独立处理，不能把用户专属信息写进缓存。
- 个人点赞/收藏/关注状态必须与公共数据分离；登录用户可按需通过轻量 Worker 接口查询状态，**不要为了匿名阅读每次自动请求个人状态接口**。点赞数量允许约定短暂延迟，不为每次点赞全量重建 R2。
- `/api/pageview` 及其他每次打开页面触发的 API 必须计入真实额度预算；提出不降低既定 UV/PV/峰值统计要求的优化选项并实际测量，不得私自删除统计功能。

### 4.3 文件键和版本

推荐初期示例（最终遵守现有 ID、分页语义，避免破坏老链接）：

```text
r2://spine-community-public-<env>/
  feeds/latest/page-1.json
  feeds/latest/page-2.json
  topics/<topic-id>/detail.json
  topics/<topic-id>/comments/page-1.json
  topics/<topic-id>/comments/page-2.json
```

- 每个对象应带 `schemaVersion`、`contentVersion`（或聚合发布版本）、`generatedAt`、`topicId`（若适用）、`data`。
- 仅保留前端必须的公开字段；避免输出整行 `SELECT *` 或当前 `decorate` 的用户定制字段。
- 分页必须稳定、可定位楼中楼，重建时一致处理“中间删除/新插入导致分页移动”。Codex 应比较 **稳定 key 重写 + Purge** 和 **版本化不可变 key + 小型索引清单** 两种实现，以**能验证的一致性与低成本**为准提出选择，不要未经测试默认其中一种完全一致。
- JSON 内容类型为 `application/json`；明确 Cache-Control、CDN TTL、浏览器缓存 TTL。**不要给浏览器设置不可控的超长缓存**；删除/隐藏时必须可及时撤回。

## 五、写入和 D1→R2 同步可靠性（必须实现）

### 5.1 D1 事务内记录待办（Transactional Outbox）

- 采用版本化的 D1 迁移增加**投影版本**及**待同步任务表（outbox）**，有目标（topic / feed 等）、目标 ID、期望版本、状态、失败次数、下次重试时间、租约/并发标识、错误摘要、更新时间；关键字段建索引，状态支持幂等处理。
- **每个会修改公开显示的数据写入路径，必须在同一次 D1 事务内**完成业务写入、版本递增和新增/合并 outbox。可考虑 `env.DB.batch()` 的事务批处理，但要验证依赖关系和错误回滚。
- 覆盖：创建/编辑/删除帖子；新增/编辑/删除回复、楼主进展；审核隐藏/恢复；用户隐私删除；Preview 导入/采集写入；公开昵称/地区变更；会影响列表排序/公开统计的其他路径。
- **导入/跨环境同步不得遗漏**：`src/import.ts`、`src/collect.ts` 及其批量导入一次可能同时插入主帖与多条楼中楼回复。按每个受影响主帖合并一个投影更新标记，不必每条评论单独重建 R2/Purge；并确保普通 API 以外的 `scripts/sync-preview-to-production.mjs` 直接 SQL 写入生产 D1 时一并产生生产 outbox，必须与该批 SQL 的提交保持原子性。跳过重复帖子时不得错误重写生产帖内容，重试则可以补偿尚未发布的投影任务。
- 回复、进展等除了标记帖子详情，还必须标记受影响的首页/分类列表；避免每条回复都刷新所有列表和所有语言投影。
- R2 写入失败**不得回滚已经成功的 D1 发帖**，也不得丢失 outbox；写入成功的接口仍给提交者返回新数据，以便页面立即局部更新。

### 5.2 处理、并发与重试

- 正常写入后尽快触发轻量同步，可评估 `ctx.waitUntil()`；**不得假定它无限期可靠**，持久 outbox 才是恢复来源。
- 同一帖子多个并发回复：对同一对象的发布任务进行串行化/互斥处理，或以带条件约束的 R2 写入防止旧版本覆盖新版本；重试时**重新读取 D1 最新状态**，不能重放过时的 JSON 快照。
- R2 写完后执行**精确 URL CDN 清理**；若清理失败，任务不得标记成功。R2 覆盖不会自动让 CDN 上旧版本消失，且缓存 404 也需要考虑。
- 标记完成前核对“已经发布/清理的版本与 D1 期望版本”；若处理期间又有新写入，保留新的待同步状态，不得用旧任务的成功标记覆盖它。
- 重试有指数退避、失败上限/死信状态、可观测日志和人工重放工具；可合并同一对象短时间内的多个更新。API Token 仅保存在 Cloudflare Secret 等安全位置，最小权限（缓存清理权限），**不可放进 R2 JSON、GitHub 或前端**。
- 失败恢复的条件是依赖服务恢复、额度允许、任务记录完整且代码正常；**不承诺任意故障下 100% 即时一致**。

### 5.3 生产 Cron 与开发测试安排（已确认）

- **生产环境只设置一个 Cron Trigger**（初始建议 `*/10 * * * *`，UTC），本阶段只检查 D1 outbox 中的待办、执行失败重试与告警，**不做 R2 全量/批量对账、不对全部对象定时执行 HEAD / LIST 或内容哈希抽查**。部署前测量 Worker Free CPU/调用、D1 rows read/written、R2 操作额度；执行任务时设置批次上限。
- **开发 Preview 不自动设置 Cron**。提供只对开发环境可用、受保护的手动触发/本地 scheduled 测试；要求可重复、无权限越界、只操作开发绑定，严禁生产写入。
- 两环境必须在源码和配置上清晰隔离，验证实际触发目标 Worker；文档提交**不会**创建 Cron，生产 Cron 开启仍须用户单独确认。
- **2026-11-08 用户明确决定：批量对账暂列待定，本轮开发先不实现。** 不做定期逐对象 `R2.head()`、`R2.list()` 扫描、D1/R2 版本抽查或全量内容摘要抽查。将来是否增加批量对账，待实际流量、费用与故障情况再单独决定。
- **本阶段局限必须写入验收报告**：若存在绕过 outbox 的 D1 直接写入，Cron 仅检查 outbox 时无法发现该遗漏。因此所有业务写入、采集导入、跨环境同步脚本的生产直接 SQL 写入，都必须与业务数据在同一事务里生成 outbox；必须进行覆盖范围审计和故障注入测试。失败或漏任务排查可以提供经授权的**按指定帖子手动补建/重发**工具，但不得暗中启动大规模自动对账。

## 六、删除、隐藏、审核和敏感内容的更严格要求

- 对 `hidden`、`pending_review`、`blocked`、未公开和本人可见等内容，**不能生成公开 JSON**。
- 原需求：主帖删除后只能公开显示“该帖子已删除”的占位，原始正文、翻译和搜索结果不能再出现；回复删除遵循已有占位规则。
- 删除/隐藏/隐私清除属于**高优先级同步**：D1 先标记，立即尝试 R2 删除或覆盖为安全占位、精确 Purge，验证公开路径（含分页、列表、译文、搜索公开缓存）已不再暴露敏感内容；失败必须留任务、重试与告警。
- **不能保证在 CDN 清理传播完成之前立即撤回全球所有旧副本**。这是公开缓存方案的真实限制；上线前应制定严格的删除可见性验收目标、最大 TTL 与应急封锁/回退机制。如果无法满足隐私需求，应将高风险内容读取保留在可鉴权的 Worker 路径，不能把直接公开的 R2 当成强一致的即时撤回机制。
- R2 自定义域名会让指定桶内对象公开可读；只向公共专用桶输出最小公开字段，不能把登录私有内容或其他业务文件放入该桶。

## 七、前端、功能完整性与降级

- 首页脚本和 HTML/CSS 可优先作为 `public/` Static Assets 直接返回，拟移除 `run_worker_first` 中 `/`、`/index.html` 之前，必须保留 Preview 的 `noindex,nofollow` 防索引处理（例如通过部署可用的静态响应头机制验证），不能为了少一次 Worker 请求放开开发站 SEO。
- 对**匿名标准列表与公开详情**使用 R2 data 域名；复杂筛选、登录权限相关内容按需走 Worker。保留现有 URL/锚点导航、分页、“查看原文”、回复定位和局部更新。
- 发帖、回复成功后当前用户先直接看到返回的内容，页面不得强制刷新；若 R2/CDN 未同步，要明确区分“已保存 D1”与“其他用户尚可能看到旧缓存”。
- R2 不可用时，提供**受控降级开关**，必要时临时切回既有 Worker+D1 只读接口，记录可能增加的 Worker/D1 额度；不能在高流量故障时无限无保护地回退，避免冲破 Free 配额。
- CDN 公共缓存与用户定制的 HTTP 响应、Cookie/Authorization 完全隔离；配置正确的 `Vary` / Cache Rule / 浏览器缓存策略，避免任何跨用户数据泄露。

## 八、额度、风险与安全前置检查

- 截至 2026-11-08 官方额度（**开工前再次核实**）：Workers Free 100,000 请求/日；D1 Free 读取 5,000,000 行/日、写入 100,000 行/日、总存储 5GB；R2 Standard 免费 10GB-month、每月 1,000,000 Class A、10,000,000 Class B 操作。超额/注册要求等需要在 Cloudflare 控制台实际确认。
- R2 **不是严格零费用承诺**。创建 R2 桶、绑定可公开访问的自定义域名、调整缓存/计费设置前必须先让用户看配置、权限、预算与风险，再执行用户授权的操作。
- 测量与告警：Worker 每日调用、Cron 次数和失败、D1 rows read/written、R2 Class A/B、存储量、CDN HIT/MISS、Purge 成功率、outbox pending/失败/最老年龄、公开投影落后版本。
- 设置批次上限、速率限制、重试上限和故障时熔断；避免异常用户或恶意重复请求驱动无限 R2 写入/缓存清理。
- 不启用用户图片上传；该功能与本次公开 JSON R2 存储是两件独立事情，维持原有禁用开关。

## 八点一、明确暂缓事项：自动批量对账（2026-11-08）

- **状态：待定／本次不做。** 不设计为本轮开发或验收的必需功能；不要借 Cron 机会定时遍历所有 D1 帖子和 R2 对象。
- 本轮仍需交付：D1 事务内 outbox + 版本号；R2 JSON 写入、CDN 缓存刷新；失败重试；生产一个 Cron（仅处理待办任务），开发手动测试；所有 D1 写入入口完整覆盖。
- 这意味着在未生成任何 outbox 的异常写入情况下，系统**不能保证自动发现或修复**，除非通过人工检查或未来单独批准开发对账功能。请 Codex 诚实地报告这一残余风险，不得声称具备全量最终一致性自愈能力。
